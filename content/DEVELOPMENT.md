# Development and deployment

The website is plain static HTML, CSS and vanilla JavaScript. All rendered pages
and assets are committed. No framework or package installation is needed to
serve it. The Markdown authoring references live in content/ alongside the phase
reports.

## Local preview

Run from the repository root:

```powershell
python scripts/serve.py
```

Open http://127.0.0.1:4174/. This preview serves the Vercel security headers,
gzip responses and custom 404 page. Use an HTTP server rather than opening
index.html as a file because the site uses root-relative clean URLs.

## Editing

- Shared design values: assets/css/tokens.css.
- Base, components and layouts: assets/css/base.css, components.css, pages.css.
- Page authoring: scripts/build-pages.py; shared markup: scripts/site_helpers.py.
- Supplied copy: content/CONTENT.md. Update the authoring markup with any approved
  edits. Most copy is authored explicitly; the Services rows and FAQ read that file.
- Browser behavior: assets/js/main.js, hero-settle.js, menu-init.js and form.js.
- Public deployment values: assets/js/config.js, generated by finalize-site.py.
- Never edit the generated assets/css/site.css directly.

### Code style

Keep source code easy to read at a glance. Use names that explain the role of a
value or element, keep one meaningful action per line, and split repeated work
into small named helpers. Prefer short comments that explain why a behavior is
needed, especially around accessibility, staging guards and fallbacks. Keep
generated files reproducible from their source files, and preserve the existing
HTML structure and copy when making a readability pass.

After changing authored pages, CSS or JavaScript, regenerate in this order:

```powershell
python scripts/build-pages.py all
python scripts/site_helpers.py
python scripts/finalize-site.py
python scripts/check-site.py
node scripts/package-site.mjs
```

The finalizer creates the combined stylesheet, critical Home CSS, CSP hashes,
asset versions and staging crawl files. Run it after JavaScript or HTML changes
so the CSP and cache versions stay synchronized. Re-running it always restores
staging crawl protection.

To regenerate logo, font, favicon or social assets, install Pillow, fontTools
and Brotli in a local ignored tools directory, then run prepare-assets.py and
brand-assets.py. Ready-to-use assets are already committed. The SVG favicon
embeds the supplied raster mark; a true vector logo was not supplied.

## Configure a form provider

The current build intentionally has no connected form endpoint or analytics.
It never pretends a staging submission was received. Without JavaScript the
staging submit buttons remain disabled. Contact email remains unconfirmed.

After selecting an endpoint that supports JSON POST and normal HTML POST:

```powershell
$env:SOUDYN_SITE_URL = 'https://your-confirmed-domain.example'
$env:SOUDYN_FORM_ENDPOINT = 'https://your-chosen-provider.example/endpoint'
python scripts/build-pages.py all
python scripts/site_helpers.py
python scripts/finalize-site.py
python scripts/check-site.py
node scripts/package-site.mjs
```

The same public endpoint is written into static form actions and config.js.
The CSP permits the selected endpoint origin. Add any provider-specific public
fields only after the provider is chosen. Do not put private credentials here.
Set provider-side honeypot rejection and rate limiting, then verify all three
real notifications. The browser honeypot alone is not server protection.

Analytics is an unconfigured slot. The browser dispatches start_project_click
and the three successful form events without personal information. The optional
Plausible event hook in main.js requires a confirmed integration before use;
no tracking script is currently loaded. Add the chosen script through config.js
and update the CSP before enabling it. Confirm its data practices in the policy.

## Checks

Static checks require only Python:

```powershell
python scripts/check-site.py
```

Optional browser QA tooling stays outside the site and deployment:

```powershell
npm.cmd install --prefix .tools/browser playwright-core@1.64.1 lighthouse@13.5.0 axe-core@4.14.0
node scripts/qa/check.mjs
node scripts/qa/home-check.mjs
node scripts/qa/form-check.mjs
node scripts/qa/page-check.mjs / /services.html /products.html /travelos.html /work.html /about.html /contact.html /privacy-policy.html /404.html
node scripts/qa/edge-cases.mjs
node scripts/qa/lighthouse.mjs
```

These scripts expect the local preview on port 4174 and installed Chrome at its
standard Windows location. Lighthouse and screenshots write into ignored .tools/.
Form tests use simulated local responses and never contact a real provider.

## Vercel preview and production

vercel.json runs node scripts/package-site.mjs and publishes dist/. The package
contains website files only; project documents and authoring scripts are excluded.
No deployment or Vercel account change has been performed in this session.

1. Connect the repository to the confirmed Vercel account and use the checked-in
   configuration. Verify its preview URL, security headers and custom 404.
2. Resolve content/CONFIRM-INVENTORY.md and content/CONTENT-CHECKLIST.md. Replace package
   placeholders, supply approved work assets, confirm contact and TravelOS facts,
   and approve the logo and final Privacy Policy.
3. Wire the real form endpoint, inbox and any selected analytics. Test normal
   HTML POST with JavaScript disabled as well as browser JSON submission.
4. Publish and link the approved Privacy Policy in the shared footer. Regenerate
   pages and hashes. Add the policy to the sitemap when it is indexable.
5. After the final staging generation, remove noindex/nofollow from indexable
   pages only; retain noindex on components-test.html and the 404 page. Replace
   robots.txt with Allow: / and the confirmed absolute sitemap URL. Keep these
   launch changes in a reviewed production commit; the staging finalizer restores
   the block if rerun.
6. Verify the canonical domain, HTTPS and chosen www/apex redirect. Replace
   sitemap lastmod with actual content update dates.
7. Run the full launch QA on production, including real iPhone/Android checks,
   screen-reader form announcements, actual inbox delivery, social preview,
   Search Console and real-user performance. Then submit the sitemap.

SEO 69 on staging is expected: the only failing Lighthouse SEO audit is the
intentional crawl/index block. Production SEO has not been measured. INP needs
real interactions or field data; a zero lab total-blocking-time result is not
an INP measurement. Real production performance must be verified on deployment.
